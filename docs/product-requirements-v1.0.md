# 1. 文档概述

## 1.1 编写目的

本文档用于明确 GeoPilot 的产品目标、用户需求、功能范围、业务规则、数据要求、非功能要求及版本规划，为产品设计、研发实现、测试验收和后续商业化提供统一依据。

本文档具有以下用途：

- 作为研发任务拆分和功能实现的依据。
- 作为前后端接口、数据库结构和诊断规则设计的依据。
- 作为功能测试、系统验收和版本发布的依据。
- 约束首版开发范围，避免过早引入复杂架构和非必要功能。
- 为后续从个人开发工具演进为可商业化的 GEO 服务平台预留扩展空间。

## 1.2 产品定义

GeoPilot 是一款面向网站所有者、开发者和网站优化服务人员的轻量级 GEO 诊断与优化辅助工具。

系统通过抓取网站公开页面，分析页面技术结构、机器可读性、语义信息和内容可理解性，识别潜在问题，输出可追溯的诊断证据和整改建议，并通过重复扫描帮助用户跟踪优化效果。

GeoPilot 不只是一个网站评分工具，而是围绕以下过程构建完整工作流：

网站接入

添加目标站点与诊断配置

网站扫描

抓取页面并执行诊断规则

问题识别

记录问题、证据、级别和建议

整改与复查

执行修复、重新扫描、比较变化

结果报告

输出诊断结果与后续优化方向

## 1.3 术语定义

| 术语     | 定义                                                                     |
| ------ | ---------------------------------------------------------------------- |
| GEO    | Generative Engine Optimization，生成式引擎优化，旨在提高内容被 AI 搜索或生成式系统理解、检索及引用的可能性 |
| SEO    | Search Engine Optimization，搜索引擎优化                                      |
| 诊断规则   | 系统用于检查网页特征并判断是否存在潜在问题的可测试规则                                            |
| 扫描任务   | 用户对某个网站发起的一次诊断执行                                                       |
| 诊断问题   | 某条规则在某次扫描中产生的具体问题记录                                                    |
| 诊断证据   | 支持问题判断的实际页面内容、HTTP 状态或请求结果                                             |
| GEO 评分 | GeoPilot 根据内部诊断规则计算的辅助评分，不代表任何外部平台的官方评分                                |
| AI 可见度 | 网站或品牌在特定 AI 搜索场景中被检索、提及或引用的观察结果                                        |

# 2. 产品目标与设计原则

## 2.1 产品目标

GeoPilot V1.0 的目标是交付一套可以在真实网站上运行、结果可追溯、问题可处理、扫描可复查的 GEO 诊断工具。

具体目标如下：

1. 能够管理网站：创建、查询、编辑和删除网站项目。
2. 能够执行诊断：对公开可访问的网站执行扫描，发现技术与内容层面的问题。
3. 能够解释结果：每个问题均包含规则编号、严重级别、目标页面、证据和整改建议。
4. 能够持续跟踪：保存历史扫描结果，比较网站优化前后的变化。
5. 能够输出报告：生成可在浏览器中查看和分享的诊断报告。
6. 能够安全运行：限制目标地址、请求时间、响应体大小、重定向和并发，防止扫描器被滥用。
7. 能够持续扩展：后续可增加多页面扫描、内容质量分析、AI 可见度记录和自动化监测。

## 2.2 设计原则

- 轻量优先：首版采用单体后端和关系型数据库，不引入不必要的中间件。
- 证据优先：每条诊断结论应能够追溯到实际观察结果。
- 可解释优先：评分必须能解释其来源，不能只输出一个没有依据的数字。
- 人工可控：整改建议用于辅助用户决策，不自动修改用户生产网站。
- 渐进迭代：优先完成核心工作流，再增加 AI 分析和商业化功能。
- 安全优先：用户提交的网站 URL 属于不可信输入，必须由服务端验证。
- 结果诚实：明确区分检测事实、规则推断和尚未验证的建议。

## 2.3 成功指标

以下为首版产品验收目标，不代表 GEO 排名提升承诺。

| 指标    | V1.0 目标               |
| ----- | --------------------- |
| 网站管理  | 支持完整 CRUD 操作          |
| 扫描执行  | 支持手动启动扫描并保存扫描记录       |
| 规则覆盖  | 所有已纳入 V1.0 的规则均有对应测试  |
| 问题可追溯 | 每条问题均关联站点、扫描记录和目标 URL |
| 报告生成  | 能够查看指定扫描对应的 HTML 报告   |
| 历史数据  | 多次扫描不会覆盖之前的记录         |
| 安全测试  | 规定的 SSRF、超时和响应体限制测试通过 |
| 启动复现  | 新环境可根据部署文档完成安装与启动     |

# 3. 用户角色与核心场景

## 3.1 目标用户

| 用户类型         | 主要需求               | 使用方式           |
| ------------ | ------------------ | -------------- |
| 独立开发者        | 快速发现网站问题，为客户提供诊断服务 | 创建网站、扫描、导出报告   |
| 中小企业网站负责人    | 了解官网存在的技术和内容问题     | 查看问题清单、组织整改、复查 |
| SEO/GEO 服务人员 | 建立诊断基线并持续跟踪效果      | 多次扫描、问题管理、报告对比 |
| 网站开发团队       | 验证发布后页面的结构和可读性     | 定期或按版本进行扫描     |
| 产品运营人员       | 改善品牌信息和内容的机器可理解性   | 后续版本的内容与实体分析   |

## 3.2 核心使用场景

### 场景 A：首次诊断一个网站

1. 用户进入工作台。
2. 点击“添加网站”。
3. 填写网站名称、网址和可选备注。
4. 系统验证 URL 并创建站点记录。
5. 用户点击“运行诊断”。
6. 系统抓取首页并执行诊断规则。
7. 系统展示评分、问题数量和整改建议。
8. 用户打开报告，查看完整诊断结果。

### 场景 B：处理网站问题

1. 用户进入网站详情。
2. 打开问题清单。
3. 根据严重级别查看问题。
4. 查看每个问题的证据和整改建议。
5. 用户在网站自身的管理系统中完成修复。
6. 用户重新扫描。
7. 系统生成新的扫描记录，供用户复查。

### 场景 C：验证优化效果

1. 用户打开网站历史扫描记录。
2. 选择不同时间的扫描结果。
3. 比较评分、问题数量和具体问题变化。
4. 判断哪些问题已消失、哪些仍然存在、哪些是新发现的问题。

其中，跨扫描差异比较属于 V1.0 的计划能力；若首版工程尚未实现，应作为开发任务补齐，不得仅凭保存了历史记录就视为已经具备完整对比功能。

### 场景 D：向客户交付诊断报告

1. 开发者选择网站和指定扫描记录。
2. 打开对应 HTML 报告。
3. 报告展示诊断范围、评分说明、问题证据和整改优先级。
4. 开发者将报告链接或文件交付给客户。

V1.0 优先保证 HTML 报告可用。PDF、带品牌模板的客户交付报告可放入后续版本。

# 5. 功能需求详细说明

## 5.1 FR-001：网站管理

### 功能目标

为每个需要诊断的网站建立独立记录，并将扫描任务、诊断问题和报告关联到该网站。

### 输入字段

| 字段     | 是否必填 | 说明               |
| ------ | ---- | ---------------- |
| 网站名称   | 是    | 用于工作台展示          |
| 网站 URL | 是    | 网站首页或主要入口 URL    |
| 备注     | 否    | 记录网站用途、业务背景或其他说明 |

### 功能要求

1. 用户可以创建网站。
2. 用户可以查看网站列表。
3. 用户可以打开网站详情。
4. 用户可以修改网站名称、URL 和备注。
5. 用户可以删除网站。
6. 系统记录创建时间和更新时间。
7. 系统应在列表中展示最近一次扫描状态。
8. 删除网站时，应明确处理其扫描记录、问题记录和相关报告数据。

### 业务规则

- 网站名称不得为空。
- URL 必须通过服务端安全校验。
- 创建成功后生成唯一站点 ID。
- 同一个 URL 是否允许创建多个项目，由产品策略决定；V1.0 默认允许，但可在界面提示已有相同 URL。
- 删除操作必须由用户主动触发，并进行二次确认。
- 删除失败时不得向用户展示删除成功。

### 验收条件

- 可以创建、查看、编辑和删除网站。
- 刷新页面后网站数据仍然存在。
- 非法输入被拒绝。
- 删除后的关联数据符合既定删除策略。

## 5.2 FR-002：网站地址与安全校验

### 功能目标

确保扫描器只访问符合安全策略的目标地址，避免成为访问内部网络的代理。

### 功能要求

1. 只允许 `http` 和 `https` 协议。
2. 拒绝包含用户名或密码的 URL。
3. 拒绝 localhost、回环地址、私网地址、链路本地地址及其他禁止访问的特殊地址。
4. 在重定向时重新校验目标地址。
5. 防止通过 DNS 解析变化绕过 IP 校验。
6. 限制重定向次数。
7. 限制连接、请求和读取超时。
8. 限制响应体大小。
9. 限制扫描任务的并发数和页面数量。
10. 生产环境应配合网络出口规则进行防护。

### 安全边界

仅在发起请求前解析一次域名是不够的。实现必须确保实际建立连接的 IP 地址也满足安全策略，并防止 DNS rebinding。

### 验收条件

- 非法协议、内网 IP 和 localhost 被拒绝。
- 公网地址重定向至禁止访问的地址时被拒绝。
- 超时或超大响应体会被终止。
- 安全失败有可理解的错误信息。
- SSRF 安全测试通过后，才允许对外开放扫描服务。

## 5.3 FR-003：扫描任务管理

### 功能目标

将一次诊断作为独立任务保存，以便追踪执行状态和历史结果。

### 扫描状态

| 状态        | 含义        |
| --------- | --------- |
| queued    | 已创建，等待执行  |
| running   | 正在执行      |
| completed | 扫描成功完成    |
| failed    | 扫描执行失败    |
| cancelled | 用户或系统取消任务 |

如果首版采用同步执行，也必须在数据库中正确记录开始时间、结束时间和最终状态。

### 功能要求

- 用户可手动启动扫描。
- 每次扫描生成唯一 ID。
- 扫描记录必须关联网站 ID。
- 系统记录开始时间、结束时间、扫描页面数、评分和摘要。
- 扫描失败时保存失败原因。
- 重复扫描必须生成新的历史记录。
- 不允许失败任务永久停留在 running。
- 前端应显示加载状态，避免用户误以为请求无响应。

### 验收条件

- 每次扫描均有独立记录。
- 成功和失败状态准确。
- 扫描结果与对应站点和扫描 ID 关联正确。
- 页面刷新后仍可查看历史记录。

## 5.4 FR-004：网站页面抓取

### 功能目标

获取网站公开页面的 HTML 和基础 HTTP 信息，为诊断规则提供统一输入。

### V1.0 范围

- 默认扫描首页。
- 获取 HTTP 状态码。
- 获取最终响应 URL。
- 获取必要的响应头。
- 读取受大小限制的 HTML 内容。
- 解析 HTML 文档。
- 记录请求失败、TLS 错误、DNS 错误和超时等情况。

### 限制

首版不保证执行 JavaScript，也不保证提取只有客户端渲染后才出现的内容。

多页面抓取、站内链接发现、抓取深度、排除路径和页面去重，应按版本规划逐步实现。

## 5.5 FR-005：诊断规则引擎

### 功能目标

对页面内容执行确定性的检查规则，生成可追溯的问题。

### 首版规则目录

| 规则编号                     | 检查内容           | 默认级别 | 触发条件             |
| ------------------------ | -------------- | ---- | ---------------- |
| HTTP_FETCH_FAILED        | 首页请求           | 严重   | 页面无法获取           |
| HTTP_STATUS              | HTTP 状态        | 高    | 页面返回非预期状态        |
| TITLE_MISSING            | 页面标题           | 高    | 缺少或为空的 title     |
| TITLE_LONG               | 标题长度           | 低    | 超过内部建议阈值         |
| META_DESCRIPTION_MISSING | 页面描述           | 中    | 缺少有效 description |
| CANONICAL_MISSING        | 规范 URL         | 中    | 未发现 canonical    |
| H1_MISSING               | 主标题            | 中    | 未发现 H1           |
| H1_MULTIPLE              | 标题结构           | 低    | 页面存在多个 H1，需要人工判断 |
| SCHEMA_MISSING           | JSON-LD        | 中    | 未发现 JSON-LD      |
| THIN_CONTENT             | 可读正文           | 中    | 提取的正文低于内部阈值      |
| RESOURCE_UNAVAILABLE     | robots/sitemap | 低    | 资源不可访问或返回异常状态    |

### 规则输出字段

每条诊断问题必须至少包含：

- 规则编号。
- 严重级别。
- 问题标题。
- 目标页面 URL。
- 诊断证据。
- 整改建议。
- 关联站点 ID。
- 关联扫描 ID。
- 问题状态。
- 创建时间。

### 规则设计原则

- 每条规则都必须有可复现的测试用例。
- 规则编号一旦发布，不应随意更改。
- 规则阈值应可配置或在文档中明确。
- 同一根因产生多个相关问题时，应避免不合理的重复扣分。
- 对不适用的规则，应允许返回“不适用”或跳过，而不是一律判定为错误。
- 没有 JSON-LD 不意味着所有网站都存在错误；没有 sitemap.xml 也不一定构成硬性问题。系统应给出合理的建议，而不是绝对化判断。

## 5.6 FR-006：评分与问题优先级

### 功能目标

提供统一、可解释的内部诊断分数，帮助用户确定整改顺序。

### V1.0 暂定算法

初始分数为 100 分，按问题严重级别扣分：

| 级别          | 暂定扣分 |
| ----------- | ---- |
| 严重 Critical | 30   |
| 高 High      | 18   |
| 中 Medium    | 10   |
| 低 Low       | 4    |

最终分数限制在 0 至 100 分之间。

### 规则要求

- 评分算法必须记录版本。
- 每个扣分项都必须能够关联到具体规则结果。
- 对同一根因的重复问题应考虑去重。
- 评分应在相同输入和相同规则版本下保持确定性。
- 报告必须说明分数属于 GeoPilot 内部评分。
- 不得将该分数称为 Google、Bing 或其他 AI 平台的官方评分。

### 重要说明

该算法属于初期启发式设计，正式发布前需要通过测试页面进行校准。评分用于诊断排序和历史趋势观察，不代表 GEO 效果或搜索排名的直接预测。

## 5.7 FR-007：诊断工作台

### 页面目标

让用户快速了解已管理的网站、诊断状态和下一步操作。

### 页面内容

- 网站数量。
- 已完成扫描数量。
- 待处理问题概况。
- 最近扫描记录。
- 网站列表。
- 添加网站入口。
- 运行诊断入口。
- 错误和空状态提示。

### 交互要求

- 用户可搜索网站名称或 URL。
- 用户可从列表进入网站详情。
- 用户可直接触发诊断。
- 未添加网站时展示引导。
- 扫描进行中时显示加载状态。
- API 不可用时显示错误信息，而不是空白页面。

## 5.8 FR-008：问题中心

### 功能目标

集中展示扫描产生的问题，并支持用户理解问题、安排整改和复查。

### 问题展示字段

| 字段     | 说明             |
| ------ | -------------- |
| 问题标题   | 简明描述问题         |
| 严重级别   | 严重、高、中、低       |
| 规则编号   | 对应规则的唯一标识      |
| 页面 URL | 问题发生的位置        |
| 证据     | 实际检测到的内容或失败原因  |
| 整改建议   | 可执行的处理方向       |
| 状态     | 待处理、处理中、已修复、忽略 |
| 首次发现时间 | 问题首次被记录的时间     |
| 最近发现时间 | 最近一次扫描发现问题的时间  |

### 功能要求

- 按网站查看问题。
- 按严重级别过滤。
- 按规则编号或标题搜索。
- 查看问题证据和建议。
- 支持更新问题状态。
- 重新扫描后，能够帮助用户识别问题是否仍然存在。

### 状态规则

| 状态  | 含义                  |
| --- | ------------------- |
| 待处理 | 尚未开始整改              |
| 处理中 | 已开始整改               |
| 已修复 | 用户确认修复，且后续扫描可提供验证依据 |
| 忽略  | 用户确认当前不处理           |

“已修复”状态应与扫描验证区分。用户手动标记已修复并不等于系统已经验证问题消失；界面应避免混淆两者。

## 5.9 FR-009：历史扫描与变化跟踪

### 功能目标

保留网站的诊断历史，帮助用户评估优化前后的变化。

### 功能要求

- 展示每次扫描的时间、状态、评分和问题数量。
- 支持打开某次扫描的完整问题结果。
- 支持比较两次扫描。
- 区分新增问题、持续存在问题和本次未再出现的问题。
- 不覆盖之前扫描的原始结果。
- 明确显示规则版本变化，避免将规则升级造成的变化误认为网站本身变化。

### 变化判定

问题匹配优先使用：

`站点 ID + 规范化页面 URL + 规则编号`

对于跨页面移动、URL 重定向或规则升级造成的匹配不确定情况，系统应允许标记为“可能变化”，而不是直接断言已修复。

## 5.10 FR-010：诊断报告

### 功能目标

输出结构清晰、能够解释诊断结果的报告。

### 报告内容

1. 网站名称和目标 URL。
2. 扫描 ID 和扫描时间。
3. 诊断评分与评分说明。
4. 规则版本。
5. 问题总数和严重级别分布。
6. 问题明细。
7. 诊断证据和整改建议。
8. 优先整改顺序。
9. 报告范围与限制说明。

### 输出格式

- V1.0：HTML 报告。
- 后续版本：JSON 导出、PDF 和客户品牌模板。

### 安全要求

- 所有动态内容必须进行 HTML 转义。
- 报告只展示与指定扫描对应的数据。
- 不能将不同扫描的结果混合。
- 报告中必须注明 GEO 诊断的能力边界。

## 5.11 FR-011：错误处理与提示

系统必须区分并处理以下错误：

- URL 格式错误。
- 目标地址被安全策略拒绝。
- DNS 解析失败。
- 连接超时。
- TLS 握手或证书错误。
- HTTP 状态异常。
- 响应体超过限制。
- 数据库连接或写入失败。
- 扫描任务失败。
- 查询资源不存在。

用户界面应显示可理解的提示，服务端日志应保留必要的诊断信息，但不能向用户暴露数据库凭据、内部网络地址、堆栈和敏感配置。

# 6. 页面与交互需求

## 6.1 页面结构

工作台

网站统计、网站列表、最近扫描

网站管理

创建、编辑、删除和查看网站

网站诊断详情

评分、扫描记录、问题摘要和运行诊断

问题中心

筛选问题、查看证据、更新状态

报告中心

查看和导出指定扫描的诊断结果

## 6.2 UI 技术约束

- React + TypeScript + Vite。
- Tailwind CSS。
- shadcn/ui 风格的基础组件。
- Lucide React 图标。
- 不使用 Ant Design。
- 保持简洁、轻量、易读的浅色界面。
- 统一按钮、输入框、表格、标签和提示的视觉规则。
- 为空状态、加载状态、错误状态和无权限状态提供明确反馈。
- 桌面端优先，同时确保窄屏下关键功能仍然可用。

## 6.3 交互规范

- 删除操作必须确认。
- 扫描按钮在请求执行期间显示进度状态。
- 重复提交应受到限制。
- 操作成功或失败必须有明确反馈。
- 用户切换站点后，展示的数据必须与当前站点一致。
- 评分和问题数量不得使用静态假数据冒充真实扫描结果。

# 7. 数据需求

## 7.1 核心实体

| 实体      | 作用          | 主要关系        |
| ------- | ----------- | ----------- |
| Site    | 网站信息        | 一个网站可以有多次扫描 |
| Scan    | 一次扫描任务及结果摘要 | 属于一个网站      |
| Page    | 单个被扫描页面     | 后续多页面版本使用   |
| Finding | 一条诊断问题      | 属于一个扫描和一个网站 |
| Report  | 报告元数据或生成记录  | 关联一个扫描      |

V1.0 的核心数据表为 `sites`、`scans` 和 `findings`。如果首版报告能够实时由扫描结果生成，可以暂不单独持久化 `reports`；如果需要历史归档、下载链接或报告模板版本，则应增加报告表。

## 7.2 数据完整性

- 每条扫描记录必须关联一个有效网站。
- 每条问题必须关联有效扫描和网站。
- 扫描结果不得被后续扫描覆盖。
- 问题记录必须保存生成该问题时的证据。
- 删除站点时必须执行事务或可靠的级联删除策略。
- 所有重要时间字段应使用统一时区存储策略，并在界面统一展示。
- 评分、规则版本和扫描状态必须具有明确的类型与取值范围。

## 7.3 数据保留

V1.0 暂不强制实现自动清理历史数据。系统应保留扫描历史，避免用户无法验证整改效果。

如果后续引入自动清理，应支持配置保留周期，并在执行前明确说明会删除哪些数据。

# 8. 技术与架构约束

## 8.1 技术选型

| 层次      | 技术             | 约束           |
| ------- | -------------- | ------------ |
| 前端框架    | React          | 使用组件化开发      |
| 前端语言    | TypeScript     | 关键数据模型使用类型定义 |
| 前端构建    | Vite           | 支持本地开发和生产构建  |
| UI 样式   | Tailwind CSS   | 统一设计规范       |
| 图标      | Lucide React   | 使用开源图标       |
| 后端语言    | Go             | 优先简单、可靠、易部署  |
| HTTP 框架 | Gin            | 提供 REST API  |
| ORM     | GORM           | 管理数据库模型      |
| 数据库     | MySQL 8        | 保存业务数据       |
| 本地部署    | Docker Compose | 简化数据库启动      |

## 8.2 架构原则

首版采用单体架构：

- 一个 Go API 服务。
- 一个 React 前端应用。
- 一个 MySQL 数据库。
- 一个扫描规则引擎。
- 一个 HTML 报告生成模块。

首版不引入 Redis、消息队列、Kubernetes 或微服务。若后续多页面扫描耗时增加，再考虑后台任务队列和独立扫描工作进程。

## 8.3 接口原则

- 使用 REST API。
- 请求与响应以 JSON 为主。
- 报告接口返回 HTML。
- 错误结构统一。
- 前后端共享稳定的数据字段约定。
- 所有需要持久化的数据必须由后端验证。
- 前端校验只能改善体验，不能替代服务端校验。

# 9. 非功能需求

## 9.1 安全性

1. 扫描器必须具备 SSRF 防护。
2. 禁止访问本机、内网、链路本地、云元数据和其他受限目标。
3. 每次重定向必须重新校验目标。
4. 通过连接层 IP 校验降低 DNS rebinding 风险。
5. 限制扫描超时、重定向、响应体、并发和页面数量。
6. 生产部署应增加网络层出口控制。
7. 报告必须进行 HTML 转义，防止存储型或反射型 XSS。
8. 数据库凭据只能通过环境配置提供，不得提交到源码仓库。
9. 对外开放时必须具备认证、授权、限流和审计能力。

## 9.2 性能要求

V1.0 采用可控的单页扫描。对于响应正常的测试网站，建议将单页扫描的常规完成时间控制在 15 秒左右；超过配置超时时间后应终止并保存失败结果。

该指标是开发验收基线，不是对任意外部网站的无条件 SLA。性能测试应使用可控测试服务，并记录网络条件。

## 9.3 可靠性

- 数据库连接失败时应明确报错。
- 扫描失败必须保存最终状态。
- 重复请求不得意外覆盖历史扫描。
- 关键数据写入失败时不得返回虚假的成功结果。
- 服务重启后，已保存的站点和扫描记录仍可查询。

## 9.4 可维护性

- 诊断规则能够独立测试。
- 核心数据模型和 API 类型清晰。
- 评分规则和规则版本有记录。
- 配置通过环境变量管理。
- 提供 README、启动说明和数据库说明。
- 关键业务逻辑应有自动化测试。

## 9.5 可用性

- 页面布局清晰。
- 核心操作路径短。
- 表单错误信息明确。
- 加载状态和空状态完整。
- 报告适合浏览器查看和打印。
- 不使用复杂、非必要的交互增加操作成本。

# 10. GEO 能力边界与产品承诺

GeoPilot 必须明确区分三类结论：

| 类型     | 示例                        | 展示要求          |
| ------ | ------------------------- | ------------- |
| 客观检测事实 | 页面没有检测到 Title；HTTP 返回 404 | 提供原始证据或明确请求结果 |
| 规则推断   | 页面正文较少，可能不利于系统理解主题        | 标明为诊断判断，并说明依据 |
| 效果预测   | 修改后可能改善内容可理解性             | 作为建议，不保证结果    |

系统不得承诺：

- 网站一定被 ChatGPT、Gemini、Perplexity 或其他 AI 系统收录。
- 网站一定获得 AI 搜索引用或推荐。
- 某个 GEO 评分必然对应特定排名。
- 单次技术扫描可以完整反映网站的 GEO 表现。

AI 可见度属于独立的观测维度，后续应结合固定问题集、指定平台、采样时间和可复现的人工或合规自动化流程进行记录。

# 11. 版本规划

| 版本   | 目标        | 主要功能                        |
| ---- | --------- | --------------------------- |
| V0.1 | 跑通最小闭环    | 网站管理、首页扫描、基础规则、问题记录、HTML 报告 |
| V0.2 | 提升诊断实用性   | 多页面扫描、问题状态、任务状态、历史差异        |
| V0.3 | 增强内容分析    | 内容结构、FAQ、实体信息和 Schema 适用性分析 |
| V0.4 | 增加 GEO 观测 | AI 可见度人工采样、品牌提及、竞品对照        |
| V1.0 | 可稳定交付     | 安全加固、认证授权、部署说明、完整测试和正式验收    |

版本号应反映真实交付能力。功能没有完成或没有通过对应测试时，不得仅因代码已存在就标记为验收通过。

# 12. 需求验收基线

V1.0 需求验收至少应覆盖以下内容：

- 网站创建、查询、编辑和删除。
- URL 安全校验。
- 手动扫描和扫描状态管理。
- 首页抓取和基础诊断规则。
- 诊断问题的证据、建议和关联关系。
- 历史扫描记录。
- 指定扫描的 HTML 报告。
- 问题筛选、状态管理和历史差异能力（若纳入 V1.0 发布范围）。
- 扫描器 SSRF、超时、重定向和响应体限制。
- API 错误处理。
- 数据持久化与关联完整性。
- 前端加载、空状态和错误提示。
- 自动化测试、启动文档和部署验证。

最终通过条件应由独立的《GeoPilot 验收标准与测试用例》进一步细化，并通过实际执行记录确认。

# 13. 待确认事项

以下事项需要在正式冻结需求前确定：

1. 首发范围：问题状态管理和历史差异是否必须进入 V1.0，还是先放在 V1.1。
2. 扫描范围：V1.0 是否仍然只扫描首页，还是直接纳入有限数量的站内页面。
3. 部署方式：首版仅本地或私有部署，还是需要直接支持公网部署。
4. 用户体系：首版是否需要登录；如果公网开放，认证与访问控制必须作为发布阻断条件。
5. 报告形式：是否只需 HTML，还是需要 JSON 导出。
6. 评分机制：是否接受当前启发式扣分方案作为初版，后续通过测试集校准。
7. AI 可见度：是否在 V1.0 纳入人工采样记录，还是作为 V1.1 功能。

## 文档结论

GeoPilot 的首要任务不是追求复杂的 AI 功能，而是先建立可靠的网站诊断闭环：管理网站、执行扫描、输出有证据的问题、协助整改、保存历史并验证变化。

在此基础上，GeoPilot 才适合逐步扩展内容分析、AI 可见度观测和面向客户的商业化报告能力。

本文件为《GeoPilot 产品需求规格说明书 V1.0》评审稿。待上述范围问题确认后，可冻结为正式需求基线，并据此编写《GeoPilot 功能实现与技术设计文档 V1.0》。

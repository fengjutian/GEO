# GeoPilot 开发规范

版本：1.0  
更新时间：2026-11-02  
适用范围：GeoPilot 仓库全部后端、核心模块与前端代码

## 1. 当前阶段与产品决策

当前阶段是 **MVP 功能验证阶段**，不是公网生产阶段。

已确认的开发决策：

> **暂不开发登录、注册、RBAC、多租户、计费与团队协作；优先验证诊断功能、数据一致性、问题闭环和前端交互。**

这意味着：

- 登录认证不是当前迭代的阻塞项，不得以“还没有登录”为由暂停功能验证。
- “暂不做登录”不等于可以降低其他安全边界；SSRF 防护、输入校验、HTML 转义、响应体限制仍为硬性要求。
- 当前版本只允许在本地或受控内网环境运行，**不得直接暴露到公网**。
- 不为登录预留猜测性的数据库字段或空接口；后续认证应通过中间件和独立资源授权层接入，避免破坏现有 API 契约。
- 恢复认证开发的触发条件：功能验证清单全部通过，且产品明确进入部署/公网阶段。

## 2. 开发优先级

按以下顺序决策，冲突时优先级高者优先：

1. **功能正确性**：诊断结果、问题状态、历史对比、报告数据必须真实、可复核。
2. **数据一致性**：扫描、问题、状态事件不能出现半写入或跨扫描污染。
3. **安全边界**：SSRF、输入大小、输出转义、依赖安全不能被绕过。
4. **前端可用性**：关键路径无阻塞，错误状态可理解。
5. **可维护性**：分层清晰、测试可运行、文档同步。
6. **性能与体验优化**：在功能正确性验证后再处理。
7. **登录与多租户**：当前阶段明确暂缓。

## 3. 功能验证清单

每个功能进入“完成”前，必须至少通过对应验证项。验证结果应记录在提交说明、PR 描述或 `docs/development-status.md` 中。

| 编号 | 验证场景 | 预期结果 | 最低验证方式 |
| --- | --- | --- | --- |
| F-01 | 创建、编辑、删除网站 | 数据持久化；非法 URL、内网地址被拒绝；删除级联清理 | API 集成测试 + 手动 |
| F-02 | 成功扫描公网站点 | 保存 `completed`、评分、最终 URL、HTTP 状态、规则版本与问题 | 集成测试 + 真实站点 |
| F-03 | DNS/TLS/超时失败 | 保存 `failed` 与明确错误码，不永久停留在 `running` | 集成测试或故障站点 |
| F-04 | 问题状态更新 | 状态同步同一指纹历史记录，写入 `issue_events`，重复提交幂等 | API 集成测试 |
| F-05 | 已修复问题再次出现 | 自动重开并写入事件，首次发现时间不丢失 | API 集成测试 |
| F-06 | 扫描历史与差异对比 | 新增、持续、未再出现数量正确；旧扫描证据不被覆盖 | API 集成测试 |
| F-07 | HTML / JSON 报告 | 只包含指定扫描数据；外部内容正确转义 | 单元测试 + 手动 |
| F-08 | 工作台统计 | 网站数、扫描数、待处理问题、平均分与数据库一致 | 集成测试 |
| F-09 | SSRF 边界 | localhost、私网、链路本地、云元数据、非 80/443 端口被拒绝 | 核心单元测试 |
| F-10 | 前端关键路径 | 网站列表、详情、扫描、问题状态、历史、报告入口可操作 | `npm run build` + 手动 |

### 手动验收前置条件

- 使用**你有权扫描的公网测试站点**，不得扫描第三方未授权目标。
- 数据库使用本地/测试实例，不使用生产数据。
- 不得通过关闭 SSRF 校验来“方便测试”；需要测试内网目标时，应在核心单元测试中使用构造的 `Page`，而不是发起真实请求。

## 4. Definition of Done

一个功能只有同时满足以下条件才算完成：

1. 代码实现完成，且符合第 6 节的分层约束。
2. 受影响的核心规则/报告有单元测试；受影响 API 有集成测试。
3. `go test ./core/... ./backend/...` 通过。
4. `go vet ./...` 通过，`gofmt` 无差异。
5. 前端 `npm run build` 通过。
6. 至少完成一次与改动对应的手动验证，并记录结果。
7. 数据库字段变更具备向后兼容的迁移/回填逻辑。
8. `API.md`、`README.md` 或对应架构/状态文档同步更新。
9. 不引入无关重构、生成物或临时测试数据。

## 5. 测试规范

### 5.1 测试分层

| 层 | 位置 | 要求 |
| --- | --- | --- |
| 核心规则/安全 | `core/scan/*_test.go` | 不依赖网络和数据库；使用构造的 `Page` |
| 报告 | `core/report/*_test.go` | 覆盖转义、统计和 JSON 结构 |
| API/业务 | `backend/internal/httpapi/api_test.go` | 使用真实 MySQL 测试库 + stub scanner |
| 前端 | `npm run build` | TypeScript 严格检查；关键交互人工验证 |

### 5.2 命令

```bash
# 一键验证（格式、vet、测试、前端构建）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1 -Integration

# API 已启动时的真实 HTTP 冒烟验证
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/smoke-api.ps1 `
  -ApiBase http://127.0.0.1:8080/api `
  -Target https://example.org `
  -FailureTarget https://expired.badssl.com

# 两模块一起测试
go test ./core/... ./backend/...

# 核心模块
cd core && go test ./...

# 后端（无 TEST_DB_DSN 时数据库测试自动跳过）
cd backend && go test ./...

# MySQL 集成测试（会清空测试库业务表）
cd backend
$env:TEST_DB_DSN="user:pass@tcp(127.0.0.1:3306)/geopilot_test?charset=utf8mb4&parseTime=True&loc=Local"
go test -count=1 -run TestAPI -v ./internal/httpapi

# 前端
cd frontend && npm run build
```

### 5.3 测试数据规则

- 集成测试必须使用专用测试库，库名建议包含 `_test`。
- 禁止将 `TEST_DB_DSN` 指向开发库或生产库。
- 测试结束后应主动清理临时服务与临时数据目录。
- 不把真实客户数据、访问令牌、数据库密码写入仓库或测试夹具。

## 6. 架构与分层规范

### 6.1 依赖方向

```text
cmd/server -> httpapi -> service -> store -> domain
                    \-> core/scan
                    \-> core/report
```

具体要求：

- `core` 不得依赖 Gin、GORM、MySQL 或应用配置。
- `domain` 只包含模型、状态、指纹、版本等纯业务定义。
- `store` 负责 SQL、迁移、回填和事务持久化；不得包含 HTTP 逻辑。
- `service` 负责用例编排、业务校验、事务边界和错误分类；不得依赖 Gin。
- `httpapi` 只做路由、参数解析、错误映射和响应；不得直接使用 GORM 或写 SQL。
- `cmd/server` 只做依赖装配和进程生命周期。
- 禁止循环依赖；禁止从下层反向导入上层。

### 6.2 新功能落地顺序

1. `domain`：模型/状态/字段。
2. `store`：查询或持久化方法。
3. `service`：用例和业务规则。
4. `httpapi`：薄处理器。
5. 前端类型、API 客户端和界面。
6. 测试与文档。

### 6.3 扩展点

- 新诊断规则：实现 `core/scan.Rule` 或 `RuleFunc`。
- 新扫描方式：实现 `service.Scanner` 接口。
- 新存储：在 `store` 增加实现，不修改 HTTP 层。
- 新报告格式：在 `core/report` 增加渲染函数，保持 DTO 中立。

## 7. Go 编码规范

- 所有 Go 文件必须 `gofmt`。
- 提交前运行 `go vet ./...`。
- 公开类型和函数必须有注释，尤其是 `core` 私有模块的 API。
- 错误必须包装上下文：`fmt.Errorf("...: %w", err)` 或 service 层错误类型。
- 数据库、HTTP 请求等阻塞操作必须接收 `context.Context`。
- 禁止 `panic` 处理可预期业务错误；只在初始化常量/不可恢复配置错误时使用。
- 不在包级变量中保存数据库连接或可变全局状态。
- 事务中包含多表写入时，必须在一个事务内完成。
- 表驱动测试优先；安全相关边界必须有负向用例。

## 8. TypeScript / 前端规范

- `strict` 模式保持开启，不使用 `any` 绕过类型检查。
- API 类型集中在 `src/types.ts`，请求封装在 `src/api.ts`。
- 业务组件与展示组件分离；通用 UI 放 `src/components.tsx`。
- 所有异步请求必须处理失败状态，向用户展示可理解的错误。
- 不在组件中硬编码 API 地址；使用 `VITE_API_BASE`。
- 外部内容只通过 React 文本节点渲染；报告类 HTML 必须由后端转义。
- 新增页面/状态必须验证移动端布局和空状态。

## 9. API 规范

- 保持现有 `/api` 路径兼容；破坏性变更必须明确记录版本影响。
- 成功响应返回资源对象或明确的聚合结构。
- 失败响应统一：

```json
{
  "code": "VALIDATION_ERROR",
  "message": "可读错误信息",
  "error": "兼容旧客户端的同义信息"
}
```

- 资源不存在返回 `404 RESOURCE_NOT_FOUND`。
- 参数/状态非法返回 `400 VALIDATION_ERROR`。
- 冲突（如扫描进行中）返回 `409` 和稳定业务码。
- 新增或修改接口必须同步 `API.md` 和前端类型。
- 当前阶段不添加认证头要求；但不得新增绕过 SSRF、越权读取或任意文件访问的接口。

## 10. 数据库规范

- 使用 GORM AutoMigrate 时，只做向后兼容的增量字段变更。
- 新字段必须允许旧数据存在；需要时编写幂等回填。
- 不在迁移中删除或重命名生产字段；先弃用、再迁移、最后删除。
- 扫描任务、问题行、状态事件的多表写入必须使用事务。
- 查询必须带 `WithContext`。
- 新增索引需说明查询场景；避免无依据的索引。
- 时间统一使用 `time.Time`；可空结束时间使用 `*time.Time`，避免 MySQL 零日期错误。

## 11. 安全规范

- 扫描目标必须经过 `core/scan` 的 URL 与连接级 IP 校验。
- 不得为测试方便关闭私网/回环地址拦截并提交。
- 响应体必须有大小上限；页面正文不完整入库。
- 报告中的网站名、标题、证据、建议必须 HTML 转义。
- CORS 使用明确 allowlist，不使用 `*`。
- 请求体大小限制必须保留。
- 不在日志中输出密码、完整 DSN、访问令牌。
- 当前无登录，禁止公网部署；如需演示，使用本地或受控网络。

## 12. Git 与提交规范

- 提交前确认 `git status` 只包含预期文件。
- 不提交 `node_modules`、`dist`、`*.exe`、`*.tsbuildinfo`、临时数据库目录。
- 提交信息使用祈使句，建议前缀：
  - `feat:`
  - `fix:`
  - `refactor:`
  - `test:`
  - `docs:`
  - `chore:`
- 一个提交聚焦一个主题；重构与功能变更尽量分开。
- 数据库迁移、API 契约变化必须在提交说明中注明。

## 13. 当前明确不做

以下内容在当前阶段不进入开发队列：

- 登录、注册、会话、密码找回
- RBAC、多租户、组织/团队成员
- 订阅、计费、用量限制
- 自动登录 AI 平台或抓取平台回答
- 自动修改客户网站内容
- 复杂工作流引擎、Redis、消息队列、Kubernetes
